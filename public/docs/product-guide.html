1. Tổng quan hệ thống

TTM Monitor theo dõi rủi ro Time to Market (TTM) của các Epic Jira: từ lúc bắt đầu triển khai (Start Date / T1) tới khi lên môi trường sản xuất (R4G Date), so với mốc chuẩn cấu hình theo Loại Epic và trạng thái. Dữ liệu được nạp định kỳ từ file CSV export từ Jira; hệ thống tự tính toán cảnh báo và hiển thị trên các màn hình giám sát.

Đối tượng dùng chính

PM/SM theo dõi Epic phụ trách, Lead theo dõi Domain, CBQL Phòng theo dõi toàn bộ; Admin/SUPERADMIN cấu hình hệ thống.

Nguồn dữ liệu

File CSV export chuẩn từ Jira, import thủ công theo lớp dữ liệu hàng ngày (data layering theo aggregated_at).

Phạm vi cảnh báo

TTM-CNTT (từ Start Date tới R4G) là trọng tâm; TTM-E2E (từ ngày duyệt ý tưởng tới Release) theo dõi song song.

Nguyên tắc tính toán

Mọi cảnh báo tính bằng ngày làm việc (bỏ Thứ Bảy/Chủ Nhật/ngày nghỉ cấu hình), tính lại theo thời gian thực mỗi lần tải màn hình.

1.1. Kiến trúc ứng dụng tổng thể (cập nhật 20/10/2026)

TTM Monitor là một ứng dụng Next.js duy nhất chạy trên Node.js: cùng một tiến trình phục vụ giao diện (các trang React) và API (Route Handler src/app/api/**/route.ts), truy vấn một CSDL PostgreSQL bằng SQL thuần qua driver pg. 3. Quy trình Import dữ liệu

Thực hiện tại màn hình Nguồn dữ liệu (route /). Mỗi lần import tạo một lớp dữ liệu gắn với một mốc thời gian tổng hợp (aggregated_at).

3.1. Mô hình import theo ngày (incremental)

File CSV hàng ngày chỉ chứa các issue có trường updated rơi vào đúng ngày import đó — không phải bản snapshot đầy đủ toàn bộ dữ liệu. Vì vậy hệ thống không dựa vào "batch mới nhất" để hiển thị, mà luôn lấy dòng dữ liệu mới nhất của từng Epic trong toàn bộ lịch sử tích lũy.

3.2. Các bước xử lý khi import (không ở chế độ "chỉ kiểm tra lỗi")

  1. Parse CSV, chuẩn hoá thành các issue thô.
  2. Từ chối import (mục 3.4): loại toàn bộ dòng của Epic bị từ chối (Epic, Story, Subtask của nó) — các dòng này không đi tiếp vào bất kỳ bước nào bên dưới, kể cả bước ghi issues.
  3. Validate từng dòng: VALID / WARNING / INVALID. Nếu có dòng INVALID, cả batch coi là FAILED và không ghi vào bảng canonical.
  4. Ghi/UPSERT vào bảng canonical issues (1 dòng / issue / batch).
  5. Liên kết quan hệ Subtask → Story → Epic trong phạm vi batch.
  6. Chạy aggregateBatchData(): tính lại 4 lớp dữ liệu tổng hợp/hậu-tổng hợp (mục 4).
  7. Dọn dữ liệu raw quá hạn lưu trữ (theo cấu hình retention), luôn bảo toàn batch mới nhất.
Chế độ “Chỉ kiểm tra lỗi” (Validate only) chỉ chạy bước 1–3, không ghi gì vào CSDL — dùng để rà soát file trước khi import thật (kết quả có báo số dòng/Epic sẽ bị từ chối).

3.3. API import tự động (script Python)

Bên cạnh form upload thủ công (session + SUPERADMIN), hệ thống có 1 endpoint riêng để 1 script Python gọi trực tiếp ngay sau khi export xong CSV từ Jira: POST /api/data-source/import/auto.

Thuộc tínhGiá trị
Xác thựcHeader Authorization: Bearer <token> — token tĩnh cấu hình qua biến môi trường IMPORT_API_TOKEN trên server (không phải session người dùng), so khớp bằng thuật toán constant-time. Sai/thiếu token → 401; server chưa cấu hình token → 503.
Payloadmultipart/form-data với field file — cùng định dạng CSV (adapter Py Jira API cố định, không truyền được adapter khác), giới hạn 2MB (thoải mái hơn nhiều so với <500KB script thường xuất ra).
Thời điểm tổng hợpaggregatedAt luôn = thời điểm server nhận request (không nhận tham số từ script) — đúng ngữ nghĩa "vừa export xong, import ngay bây giờ".
Pipeline xử lýGọi lại đúng processImport() dùng chung với form thủ công — cùng bước validate → issues → aggregateBatchData() → dọn dữ liệu quá hạn (mục 3.2). Không có chế độ "chỉ kiểm tra lỗi" ở API này.
Truy vếtBatch tạo ra được đánh dấu nguồn AUTO, người thực hiện hiển thị "Python Script (Auto Import)" trong Nhật ký lịch sử import — phân biệt rõ với batch import thủ công qua UI.
Phản hồiTrả về cùng cấu trúc JSON kết quả import (status, totalRows/successRows/warningRows/errorRows, …) như API import qua UI — script có thể tự xác định thành công/thất bại theo status/mã HTTP mà không cần đăng nhập giao diện.
Endpoint này được liệt kê riêng trong danh sách route công khai (không qua kiểm tra session đăng nhập của lớp middleware nội bộ) — hệ thống middleware của ứng dụng chỉ hiểu xác thực bằng session, nên mọi route dùng bearer token đều phải khai báo tường minh để không bị chặn 401 trước khi vào tới route handler.

3.4. Từ chối import — phạm vi dữ liệu nguồn (từ 14/10/2026)

Crawl tool chưa lọc được dữ liệu ngay từ nguồn Jira, nên import adapter tự giữ phạm vi dữ liệu: chỉ nhận Epic có created ≥ 31/01/2026, Epic Released / MVP Done chỉ khi chuyển sang status đó sau 30/06/2026, và issue cấp 1 chỉ nhận issue type Epic (không nhận CTNB, YCPT…). Mọi lần import (form thủ công và API tự động) đều đi qua bước này, ngay sau khi parse CSV (bước 2 ở mục 3.2).

Epic chỉ được nhận nhờ ngoại lệ của rule BImport bình thường và tự thêm vào danh sách với “Cho phép import” bật (nguồn “Miễn rule B”, lý do ghi ngày làm bằng chứng) — để vẫn được miễn khi lịch sử làm bằng chứng đã hết hạn lưu trữ hoặc bị “Xóa lớp dữ liệu” (từ 19/10/2026). Từ 20/10/2026 dòng “Miễn rule B” chỉ miễn rule B — rule A và rule loại issue vẫn được xét ở mỗi lần import; “Cho phép import” do admin bật mới miễn mọi rule.

Epic deletion — xóa vĩnh viễn một Epic khỏi CSDL:

  • Phạm vi: Epic, các Story, các Subtask gắn thẳng vào Epic và Subtask của các Story đó — xác định theo trạng thái mới nhất của từng issue (issue đã chuyển sang Epic khác trên Jira được giữ nguyên).
  • Xóa ở mọi lớp dữ liệu: issues (mọi batch), và các bảng theo Epic: epic_alert_timeline, epic_alert_row_cache, black_listed_epics. Mỗi Epic xóa ghi 1 dòng audit_logs (EPIC_DELETION).
  • Không tự chạy lại cache. Các cache tổng hợp toàn công ty (TTM-Index, TTM Dashboard 2) vẫn tính Epic đã xóa cho tới khi admin chạy lại cache thủ công — sau mỗi lần xóa, màn hình hiện toast nhắc việc này.
  • API (SUPERADMIN): GET /api/data-source/epic-deletion?keys=… (xem trước danh sách issue key và số dòng mỗi bảng), POST /api/data-source/epic-deletion { epicKeys } (xóa).
Bỏ một Epic khỏi danh sách không làm dữ liệu quay lại: import hằng ngày chỉ chứa issue được cập nhật trong ngày, nên Epic chỉ quay lại khi được sửa trên Jira hoặc khi import lại toàn bộ. Nếu Epic vẫn vi phạm rule A/B, lần import sau sẽ lại tự từ chối nó — muốn giữ Epic, hãy bật “Cho phép import” thay vì xóa khỏi danh sách.

6. Vòng đời & lưu trữ dữ liệu

6.1. Lưu trữ dữ liệu import (raw)

Cấu hình tại panel “Lưu trữ dữ liệu import” (right panel màn hình Nguồn dữ liệu, SUPERADMIN): số ngày giữ dữ liệu raw (import_batches/issues), mặc định 30 ngày, tối thiểu 7. Việc dọn các batch / phiên bản issues cũ hơn ngưỡng chạy trong job dọn dẹp mỗi ngày nhưng chỉ khi SUPERADMIN bật “Dọn tự động” ở tab “Dọn lịch sử” (từ 26/10/2026; mặc định TẮT) — xem mục 6.5. Batch mới nhất luôn được bảo vệ để tránh mất nguồn cảnh báo hiện hành.

6.2. Lịch sử Issue chỉ còn trong issues

Từ 23/10/2026 hai bảng snapshot (epic_ttm_snapshots, issue_daily_snapshots) và panel “Nhật ký lớp dữ liệu tổng hợp (Epic)” (Xoá / Chạy lại) đã được gỡ: các bảng này chỉ là bản sao của issues và không màn hình nào đọc chúng. Lịch sử Issue (lớp dữ liệu cũ, bằng chứng rule B của Từ chối import) vì vậy chỉ tồn tại trong issues theo thời hạn lưu ở mục 6.1 (từ 24/10/2026 được làm thưa mỗi ngày: đầy đủ 30 ngày import gần nhất, xa hơn chỉ phiên bản có hiệu lực vào ngày làm việc cuối mỗi tuần và phiên bản mới nhất của mỗi issue; màn chọn ngày đọc "trạng thái tại ngày X"); dòng thời gian cảnh báo (epic_alert_timeline) vẫn được giữ sau khi raw bị dọn.

6.3. Xoá N lớp dữ liệu gần nhất

Thao tác riêng biệt (cùng màn hình, chỉ SUPERADMIN), xoá vĩnh viễn dữ liệu raw (đợt import import_batches và issues của chúng) của N "lớp dữ liệu" gần nhất, trong đó một lớp dữ liệu là một ngày có đợt import. Dòng thời gian cảnh báo (epic_alert_timeline) được giữ nguyên. Có bước xem trước (preview) số đợt import và số dòng issues sẽ bị xoá trước khi xác nhận. Dùng khi cần loại bỏ hẳn một đợt dữ liệu lỗi, thao tác này không thể hoàn tác.

6.4. Cache dữ liệu dẫn xuất & khoá tạo lại cache (từ 05/10/2026)

Các màn hình không tính trực tiếp từ dữ liệu import mà đọc 3 cache: epic_alert_row_cache (dòng Epic), ttm_index_global_cache (chỉ số toàn công ty) và ttm_dashboard_2_cache (TTM Dashboard 2). Cả 3 được tạo lại cùng nhau khi: import dữ liệu xong; lần tải trang đầu tiên của mỗi ngày (daily_cache_runs); lưu "Phạm vi dữ liệu cho TTM", Domain (đổi danh sách dự án; đổi tên, bật/tắt, xoá — khi Domain có dự án đang active), "Epic ngoại lệ", một dự án (tạo / import / xoá, đổi tên, Key, Domain, trạng thái hoặc trường Time to Market), hoặc PM/SM của dự án ở màn Quản lý User (đổi danh sách dự án của user, đổi họ tên / xoá user đang là PM/SM); lưu Rule Management; hoặc bấm "Tạo lại cache" ở Quản trị nguồn dữ liệu. Một lượt mất khoảng 20–45 giây.

  • Chỉ một lượt chạy tại một thời điểm trên mọi instance, điều phối bằng bảng derived_cache_refresh_lock. Yêu cầu đến trong lúc đang chạy không chạy song song mà được "gộp": lượt đang chạy sẽ chạy lại thêm một lần với dữ liệu mới nhất trước khi nhả khoá, nên không yêu cầu nào bị mất. Nút "Tạo lại cache" báo rõ khi yêu cầu bị gộp.
  • Tự phục hồi: nếu lượt đang chạy bị chết giữa chừng (hết thời gian chạy của function), khoá hết hạn sau 6 phút; trạng thái này được coi là cache cũ và lần tải trang kế tiếp sẽ chạy lại, kể cả khi lượt trong ngày đã thành công.
  • Thay đổi rule của Scoring Service hoặc cấu hình loại trừ chỉ thể hiện trên số liệu sau lần tạo lại cache kế tiếp.
  • Chỉ import CSV và lượt đầu ngày tự tạo lại cache (có chủ đích, từ 27/10/2026): lưu người dùng / PM-SM, dự án, Domain, Epic ngoại lệ (kể cả công tắc ở Duyệt Epic), Phạm vi dữ liệu cho TTM, Rule Management, khôi phục file backup, và cả Tiêu chí Time to Market / Bộ ngân sách / mốc Cảnh báo muộn (%) không còn tự tạo lại cache. Mỗi lần lưu như vậy chỉ hiện toast cảnh báo “cần tạo lại cache” — SUPERADMIN tự bấm "Tạo lại cache" khi chỉnh xong. Với các thay đổi hệ thống không suy ra được từ cấu hình chấm điểm (người dùng, dự án, Domain, Epic ngoại lệ, phạm vi, nhóm rule, backup), lần lưu ghi một dấu “cache cũ” (cột stale_since / stale_reasons của derived_cache_refresh_lock); dấu xoá khi một lượt tạo lại bắt đầu sau lần lưu đó kết thúc. Hệ thống tự nhận biết cache đang cũ so với cấu hình: mỗi lượt tạo cache ghi lại phiên bản cấu hình (mã rule + dấu vân tay của Tiêu chí TTM, bộ ngân sách, mốc cảnh báo, phạm vi, nhóm rule kể cả điều kiện TTM-applied, ngày nghỉ / làm bù); khi cấu hình hiện tại khác phiên bản đó, chấm đỏ hiện ở tab "Theo dõi cache dữ liệu" và ở mục "Nguồn dữ liệu" trên left panel (cả nhóm "SuperAdmin: Quản trị hệ thống"); bấm mục đó sẽ mở thẳng tab cache. Chấm đỏ tự tắt sau khi tạo lại cache.
  • Domain của dự án là thông tin hiện hành, không lưu theo lịch sử: mỗi dòng Epic mang tên Domain hiện tại của dự án (dự án và Domain đều phải đang active). Dự án bị gỡ khỏi Domain (hoặc Domain bị tắt / xoá) thì sau lần tạo lại cache, Epic của dự án đó không còn tính vào thống kê của Domain cũ — bộ lọc Domain, dòng Domain trong Ma trận Phân bổ, pie chart "Theo Domain nghiệp vụ" — mà chuyển sang nhóm "Chưa gán Domain"; tổng toàn phòng không đổi. ADMIN của Domain cũ cũng không còn thấy các Epic đó (trừ khi là PM/SM của dự án). Xem lại lớp dữ liệu cũ vẫn dùng Domain hiện hành.

6.5. Tab “Dọn lịch sử” — công tắc an toàn khi xoá lịch sử issues (từ 26/10/2026)

Xoá bớt phiên bản issues cũ (mục 6.2) là thao tác không hoàn tác, và lần dọn đầu tiên trên một CSDL chưa từng dọn có thể xoá hàng loạt dòng. Vì vậy việc dọn tự động hằng ngày mặc định TẮT và được điều khiển ở tab Dọn lịch sử của màn Quản trị nguồn dữ liệu (chỉ SUPERADMIN):

  • Dọn tự động hằng ngày — Bật / Tắt. Khi tắt, job hằng ngày vẫn ghi các mốc ngày hàng tuần (dòng nhỏ) nhưng không xoá dòng nào. Bật sẽ có hộp xác nhận nhắc sao lưu và xem trước.
  • Tối đa số dòng xoá mỗi lượt (1.000 – 1.000.000, mặc định 50.000): mỗi lượt chỉ xoá tối đa ngần ấy dòng (dòng cũ nhất trước); phần còn lại chờ lượt ngày hôm sau. Backlog lớn vì thế được dọn dần qua nhiều ngày, không dồn vào một câu lệnh dài.
  • Lượt dọn gần nhất: thời điểm, nguồn (tự động / dọn tay), số dòng đã xoá và số dòng còn chờ.
  • Xem trước: chỉ đếm — số dòng sẽ xoá (cũ hơn thời hạn / nằm giữa các mốc tuần), số đợt import trống, số dòng được giữ; kèm số lượt cần để dọn hết với giới hạn hiện tại.
  • Dọn một lượt (dọn tay): sau khi xem trước, xoá một lượt tối đa bằng giới hạn trên, có hộp xác nhận; bấm lại cho tới khi hết. Muốn xoá hết trong một lần: nút “Xóa … phiên bản issues cũ” ở tab Import & Dọn dữ liệu của màn Sao lưu / Phục hồi dữ liệu.

Quy trình khuyến nghị cho lần dọn đầu tiên: (1) sao lưu CSDL → (2) Xem trước, kiểm tra số dòng → (3) bật Dọn tự động, hoặc dọn tay từng lượt. Dữ liệu cấu hình nằm ở các cột history_thinning_* của bảng data_retention_configs.

7. Cấu hình chính sách TTM & rule cảnh báo

Tại màn hình Cấu hình cảnh báo (/admin/status-alert-rules) có 2 nhóm cấu hình độc lập:

7.1. Tiêu chí Time to Market (TTM Policy)

Xác định deadline tổng thể: Target = From TTM Field + số ngày làm việc, theo từng cặp (Loại TTM × Loại Epic). From TTM Field/To TTM Field là nhãn logic nội bộ ứng dụng (Start Date, Idea Approved Date, R4G Date, Due Date) — không phải tên cột trong file CSV import gốc. Loại TTM gồm TTM-CNTT (T1 → R4G, trọng tâm MVP1) và TTM-E2E (T0 → Release).

7.2. Rule cảnh báo theo trạng thái Epic (epic_status_alert_rules)

Với mỗi cặp (Loại Epic × Trạng thái Epic), cấu hình 2 mốc — Cảnh báo sớm tính bằng số ngày làm việc kể từ T1; Cảnh báo muộn (từ 26/10/2026) tính bằng % ngân sách TTM-CNTT của Epic: mốc = Start Date + ⌈% × N⌉ ngày làm việc, N theo bộ ngân sách mà rule TTM-CNTT của Epic đọc, nên đổi ngân sách (ví dụ 30 ngày) thì mốc muộn tự co giãn. Dữ liệu cũ được đổi sang % theo ngân sách Mặc định (mốc không đổi). Mốc Fail TTM-CNTT không còn nằm ở bảng này (cột fail_offset_days đã bị bỏ) — Fail TTM-CNTT/ TTM-E2E lấy hoàn toàn từ Tiêu chí Time to Market ở mục 7.1. Design và In Progress là dữ liệu seed mặc định; có thể thêm rule cho trạng thái khác (IN PO, DEV, TEST, PENTEST, R4GOLIVE, MVPDONE, Released…).

7.3. Phân loại 4 Epic Type (CT-Lv12 / CT-Lv34 / SP-Lv12 / SP-Lv34)

Mọi mốc cảnh báo ở trên áp dụng theo 4 Epic Type (cập nhật từ 09/2026, xem chi tiết tại chương 5.2) — được tính tự động lúc import dữ liệu bằng hàm computeEpicComplexity:

  • CT-Lv12: Loại yêu cầu ∈ {Tính năng mới, Cải tiến} & Level ∈ {1, 2} (mặc định cho trường hợp dữ liệu thiếu hoặc không khớp).
  • CT-Lv34: Loại yêu cầu ∈ {Tính năng mới, Cải tiến} & Level ∈ {3, 4}.
  • SP-Lv12: Loại yêu cầu ∈ {Sản phẩm/dịch vụ/quy trình mới, Sản phẩm} & Level ∈ {1, 2}.
  • SP-Lv34: Loại yêu cầu ∈ {Sản phẩm/dịch vụ/quy trình mới, Sản phẩm} & Level ∈ {3, 4}.
Hạ tầng CSDL đã nới rộng CHECK constraint trên bảng epic_status_alert_rules để đón nhận cả 4 loại mới này song song với các dòng legacy SIMPLE/COMPLEX cũ (giữ lại cấu hình cũ để tham chiếu). Admin có thể cấu hình chi tiết offset cảnh báo sớm/muộn cho 4 loại Epic Type mới trực tiếp trên màn hình Cấu hình cảnh báo.

7.4. Rule object & Nhóm rule — màn hình Rule Management (từ 25/10/2026)

Rule đánh giá Epic thường chỉ có hiệu lực theo thời kỳ (ví dụ Epic bắt đầu từ 01/09/2026 dùng chuẩn TTM-CNTT khác Epic cũ). Từ 25/10/2026 Scoring Service tổ chức rule thành Rule object và chấm mỗi Epic theo các nhóm rule (Rule Group) mà Epic khớp (phân lớp, từ 26/10/2026). Thiết kế đầy đủ: docs/superpowers/specs/2026-10-25-rule-groups-design.md.

  • Rule object = một đơn vị logic phát ra một nhóm badge, có mã cố định (lưu trong CSDL, không đổi) và tên hiển thị. Logic viết trong code; không có trình soạn rule trên giao diện. Sửa một rule = sửa tại chỗ theo mã, mọi nhóm đang chọn mã đó dùng logic mới; logic chỉ áp dụng cho một giai đoạn Epic thì tạo biến thể với mã mới (ví dụ ttm-cntt-2027).
  • Rule chọn được (theo nhóm): ttm-cntt-sep-2026 (Đạt / Fail TTM-CNTT (QLDA) + Sai Status), ttm-e2e-july-2026 (Đạt / Fail TTM-E2E + Sai Status), R1, R2, R3, R4, R5, R6, R8, R9, R10 (mỗi rule kèm khuyến nghị của nó), Thiếu lý do Fail TTM (khâu fail), Thiếu phòng chịu TN chính, Giải trình Golive, Chờ golive. Mỗi rule chọn được nằm trong một slot (vị trí): rule TTM-CNTT (QLDA) và TTM-E2E, và từng rule còn lại đều có slot riêng. Mỗi nhóm bật tối đa 1 rule cho mỗi slot; các biến thể của một slot phát cùng badge nên phễu và chỉ số đếm như cũ.
  • Rule luôn chạy (mọi Epic): Không áp dụng / Không tính được TTM-CNTT và TTM-E2E, Baseline từ ngày tạo Jira + Bổ sung T0, Cảnh báo muộn, Sai Status (Release), Release đúng hạn (badge vẫn tắt), Phạm vi dữ liệu cho TTM / Epic ngoại lệ, Pha.
  • Nhóm rule: tên, thứ tự ưu tiên, master toggle bật/tắt, điều kiện ngày Epic (5 cặp Từ ngày / Đến ngày: Ngày tạo, Ngày phê duyệt ý tưởng, Start Date, R4G Date, Due Date — kết hợp AND, tính cả hai đầu, ô trống = không giới hạn) và trạng thái từng rule: Kế thừa / Bật / Tắt. Một Epic được chấm theo mọi nhóm bật mà nó khớp mọi điều kiện (Epic thiếu ngày mà nhóm có điều kiện thì không khớp nhóm đó), xếp từ ưu tiên cao xuống thấp, Default luôn là lớp cuối — bắt buộc tồn tại, không xoá / đổi tên / tắt, không có điều kiện ngày (chỉ sửa được danh sách rule Bật / Tắt). Với mỗi rule (slot), nhóm gần nhất khai báo rule đó quyết định: Bật = áp dụng cho Epic của nhóm; Tắt = không áp dụng, kể cả khi nhóm dưới hoặc Default bật; Kế thừa = theo nhóm dưới. Ví dụ: nhóm "R4G < 01/09/2026" chỉ cấu hình rule 1 thì các rule khác của Epic đó tự rơi xuống nhóm gần nhất rồi Default. Nhóm đầu tiên Epic khớp là nhóm chính (hiện ở cột Nhóm rule, chiều "Theo Nhóm rule"). Epic ngoại lệ không thuộc nhóm nào (không được xét). Khi bấm Lưu, nếu hai nhóm có thể cùng khớp một Epic mà khai báo khác nhau cho cùng một rule/slot, màn hình hiện popup cảnh báo xung đột (Epic theo nhóm ưu tiên cao hơn) để xác nhận. Từ 26/10/2026, nhóm (không phải Default) không có điều kiện nào — ngày hoặc TTM-applied — không lưu được: nhóm như vậy khớp mọi Epic và che mọi nhóm ưu tiên thấp hơn; rule muốn áp dụng cho mọi Epic thì khai báo ở Default.
  • TTM-applied / Kế hoạch ngoại lệ TTM (từ 26/10/2026): trường TTM-applied của Epic = Ngoại lệ thì Target TTM-CNTT lấy theo ngày except-TTM-plan (rule ttm-cntt-except-plan, chọn bằng nhóm rule có điều kiện "TTM-applied = Ngoại lệ", đặt trên các nhóm khác); thiếu / sai ngày plan là Sai lệch dữ liệu R11. Trống, None, Theo quy định hoặc giá trị lạ → tính theo rule chung. TTM-applied = Không áp dụng → import tự đưa Epic vào danh sách Epic ngoại lệ (black list); Epic thêm tay không bị import gỡ.
  • Bộ ngân sách (từ 26/10/2026): Cấu hình cảnh báo → Tiêu chí Time to Market có thể có nhiều bộ; bộ DEFAULT là cấu hình hiện hành, bộ khác chỉ khai báo các dòng khác Mặc định (dòng thiếu kế thừa Mặc định). 8.4. Kết luận được tính sẵn và lưu cache (thay cho "tính real-time")

Các màn hình không tính lại cảnh báo ở mỗi lần tải trang nữa. Scoring Service chấm mọi Epic một lần rồi lưu vào cache dẫn xuất (epic_alert_row_cache, ttm_index_global_cache, ttm_dashboard_2_cache) — Quản trị Epic, Chuẩn hoá dữ liệu, TTM Dashboard 2, Báo cáo Epic và MCP đọc từ đó (mục 6.4). Cache được tạo lại:

  • sau mỗi lần import (thủ công hoặc API tự động);
  • một lần đầu mỗi ngày (lượt đầu ngày do lần tải trang đầu tiên kích hoạt) — để Cảnh báo muộn, Fail theo ngày hiện tại tự cập nhật dù không import;
  • khi lưu "Phạm vi dữ liệu cho TTM", "Phạm vi rule Sai lệch dữ liệu", Epic ngoại lệ, cờ Time to Market / Domain / PM-SM của dự án;
  • khi SUPERADMIN bấm "Tạo lại cache" (Quản trị nguồn dữ liệu → Theo dõi cache dữ liệu).

Mỗi lần chỉ một lượt tạo lại chạy (khoá derived_cache_refresh_lock); yêu cầu đến trong lúc đang chạy được gộp, lượt đang chạy sẽ chạy thêm một lần với dữ liệu mới nhất. Mọi màn hình hiện chỉ báo "Hệ thống đang tính toán lại cache" khi có lượt đang chạy. Rule mới chỉ có hiệu lực sau lần tạo lại cache kế tiếp. Xoá Epic (Từ chối import / Epic deletion) không tự tạo lại cache.

8.5. Cách tính ngày baseline từng pha (màn hình Quản trị Epic)

5 ngày baseline pha (DESIGN/DEV/TEST/PENTEST/R4GOLIVE) được suy ra tuần tự từ Start Date (T1), cộng dồn số ngày làm việc theo tỷ trọng 20% / 30% / 30% / 10% / 10% trên tổng số ngày làm việc TTM-CNTT của Epic (15, 25 hoặc 30 ngày tuỳ Loại Epic, mục 5.2/7.1). Vì tỷ trọng từng pha thường ra số ngày lẻ, hệ thống làm tròn theo từng pha để tổng cộng dồn luôn khớp chính xác tổng số ngày TTM-CNTT:

  • DESIGN: làm tròn lên (ceiling).
  • DEV, TEST, PENTEST: làm tròn xuống (floor), tính tiếp nối từ ngày cộng dồn của pha trước.
  • R4GOLIVE: không dùng số ngày làm tròn theo chuỗi tích luỹ ở trên — được gán trực tiếp bằng Start Date + (tổng số ngày làm việc TTM-CNTT − 1) ngày làm việc, để đảm bảo ngày baseline R4GOLIVE luôn trùng khớp tuyệt đối với Target TTM-CNTT tổng (mục 7.1), không lệch do sai số làm tròn cộng dồn qua 4 pha trước.
Ví dụ Epic SP-Lv12 / SP-Lv34 (30 ngày TTM-CNTT): DESIGN chiếm ⌈30×20%⌉ = 6 ngày; DEV/TEST mỗi pha làm tròn xuống theo tỷ trọng 30%; PENTEST làm tròn xuống theo 10%; R4GOLIVE luôn rơi đúng ngày làm việc thứ 29 kể từ Start Date (30 − 1), bất kể tổng 4 pha trước cộng dồn ra bao nhiêu ngày.

8.6. Trục Release — "Chờ golive" / "Cảnh báo sớm" / "Giải trình Golive" (từ 24/09/2026, "Chờ golive" đổi rule 01/10/2026)

Badge thứ 3 ở cột Nhận xét, hoàn toàn độc lập với Fail TTM-CNTT/Fail TTM-E2E (mục 8.3) và với "Sai lệch dữ liệu" (mục 9).

Cập nhật 01/10/2026 (chỉ Scoring Service — chế độ hiển thị đang active): "Chờ golive" không còn phụ thuộc R4G Date/hạn 5 ngày nữa, chỉ còn xét status và Phạm vi dữ liệu cho TTM (QLDA): status = R4GOLIVE HOẶC (status = RELEASED VÀ chưa có Due Date), và Epic phải nằm trong "Phạm vi dữ liệu cho TTM (QLDA)" (Epic ngoài phạm vi thì ẩn badge này, giống hệt cách TTM-CNTT bị ẩn khi ngoài phạm vi). Vì không còn mốc ngày, badge này giờ có thể hiện đồng thời với "Giải trình Golive" trên cùng 1 Epic (trước đây 2 badge loại trừ nhau tuyệt đối). 8.7. Chỉ số TTM-CNTT (QLDA), TTM-CNTT (QA), TTM-E2E — công thức, phạm vi tính và "Phạm vi dữ liệu cho TTM" (cập nhật 04/10/2026)

Toàn bộ ứng dụng thống nhất 3 chỉ số: TTM-CNTT (QLDA) (tên cũ TTM-Index), TTM-CNTT (QA) (tên cũ QA-Index) và TTM-E2E.

Công thức TTM-CNTT (QLDA) và TTM-CNTT (QA) — từ 04/10/2026 (tên các tiêu chí L01–L05bb: xem mục 21.2):

Tỷ lệ % Pass TTM-CNTT = L05aa / (L05aa + L05ab + L05ba) × 100
Tỷ lệ % Fail TTM-CNTT = (L05ab + L05ba) / (L05aa + L05ab + L05ba) × 100
  • L05aa — Epic đạt TTM-CNTT: có R4G Date, đã tới ngày và không muộn hơn Target R4G.
  • L05ab — Epic không đạt TTM-CNTT (nhóm 1): có R4G Date nhưng muộn hơn Target R4G.
  • L05ba — Epic không đạt TTM-CNTT (nhóm 2): chưa có R4G Date và đã quá Target R4G.
  • Chỉ Epic đã có kết luận mới vào mẫu số. Không tính: Epic Cancelled, Epic Sai lệch dữ liệu, Epic ngoài "Phạm vi dữ liệu cho TTM", Epic không tính được Target (L05ac; Epic có R4G Date còn ở tương lai là Sai lệch dữ liệu từ 09/10/2026), Epic chưa có R4G Date và chưa quá Target (L05bb).
  • Con số hiện cạnh chỉ số (ví dụ 120/150) là L05aa / (L05aa + L05ab + L05ba). Khi chưa có Epic nào được kết luận, chỉ số hiện 100%.
  • Trước 04/10/2026 công thức là pass/eligible với eligible = mọi Epic có R4G Date và không sai lệch dữ liệu — tức mẫu số gồm cả Epic R4G tương lai (L05ac) và không gồm Epic Fail chưa có R4G Date (L05ba).

Hai chỉ số dùng chung công thức trên, chỉ khác nhau ở tập Epic được xét; từ 05/10/2026 TTM-E2E cũng dùng công thức này trên kết luận của trục E2E — Đạt TTM-E2E / (Đạt TTM-E2E + Fail TTM-E2E), gồm cả Epic Fail chưa có R4G Date, không áp "Phạm vi dữ liệu cho TTM":

Trong tài liệu này, "TTM-CNTT" không kèm hậu tố cũng hiểu là TTM-CNTT (QLDA). TTM-CNTT (QA) chỉ dùng ở các vị trí chỉ định: chỉ số TTM-CNTT (QA) (widget/vòng KPI, cột ma trận TTM Dashboard), khoảng ngày "R4G for TTM (QA)" và badge ghi chú "Ngoài phạm vi QA" trong danh mục Logic cảnh báo.

Phạm vi dữ liệu: nếu không nói rõ khác, các chỉ số luôn tính trên đúng tập Epic mà bảng/màn hình đang hiển thị — theo quyền dữ liệu của người xem và mọi bộ lọc đang chọn (1 Epic, 1 dự án, 1 domain, 1 PM/SM, khoảng thời gian...). Ví dụ: widget TTM-CNTT (QLDA)/TTM-CNTT (QA) trên banner "Quản trị Epic" tính theo bảng Danh sách Epic đang lọc; 2 vòng chỉ số trong KPI của TTM Dashboard tính theo bộ lọc Dự án/Domain/PM-SM của Dashboard.

Ngoại lệ: 2 widget cố định trên banner TTM Dashboard — TTM-CNTT (QLDA) và TTM-CNTT (QA) — tính trên toàn bộ Epic trong ứng dụng (vẫn theo rule phạm vi của chỉ số), không phụ thuộc quyền hay bộ lọc: cùng 1 giá trị với mọi người dùng, có cache (tính lại sau mỗi lần import/khi Admin lưu cấu hình mục dưới). Epic Cancelled luôn bị loại khỏi mọi chỉ số (không tính tử số lẫn mẫu số). Xem brd/16-ttm-indexes.md để có công thức đầy đủ kèm bảng liệt kê mọi trường hợp bị loại khỏi phạm vi tính toán.

"Phạm vi dữ liệu cho TTM" (panel mới ở "Cấu hình cảnh báo"): Admin có thể giới hạn thêm — chỉ Epic có R4G Date (hoặc, nếu chưa có, mốc mục tiêu TTM-CNTT) nằm trong khoảng ngày A–B (tính cả ngày A và B) mới được tính vào TTM-CNTT (QLDA); khoảng ngày C–D riêng cho TTM-CNTT (QA). Để trống = không giới hạn (mặc định, không đổi hành vi hiện tại). Epic ngoài phạm vi này hiện badge "Ngoài phạm vi TTM-CNTT" ở cột Nhận xét thay vì Fail/Late/Early/Đạt — vẫn hiển thị trong bảng, chỉ ẩn phán quyết TTM-CNTT. Lưu cấu hình sẽ tự động tính lại và lưu cache ngay. Dashboard 2 có thêm mục "Advanced Filters" (thu gọn mặc định) cho phép người xem tạm thời ghi đè khoảng ngày này riêng cho phiên xem của mình (không lưu lại), và mang theo đúng khoảng ngày đó khi bấm vào 1 số liệu để mở "Quản trị Epic" xem chi tiết.

10. Lịch sử cảnh báo tích luỹ

Khác với cảnh báo hiển thị trên bảng (tính real-time), lịch sử cảnh báo "đóng băng" đúng trạng thái cảnh báo tại ngày import: mỗi khi Epic được tính là Cảnh báo muộn hoặc Fail TTM ở một lần import, hệ thống mở (hoặc kéo dài) một "đợt" cảnh báo trong epic_alert_timeline gồm loại cảnh báo, ngày bắt đầu/kết thúc và trạng thái Epic lúc đó — tích luỹ theo thời gian để tra cứu sau này.

Dữ liệu này phục vụ trên màn hình Quản trị Epic:

  • Quy tắc hiển thị Epic Released trên "Quản trị Epic (rút gọn)": chỉ hiện nếu Epic từng có ít nhất một đợt Cảnh báo muộn / Fail TTM-CNTT.
  • Panel "Epic History" liệt kê các đợt cảnh báo (từ ngày – đến ngày/nay, status) cùng các mốc hoàn thành, sắp xếp theo thời gian.

Bảng epic_alert_history (mỗi lần cảnh báo một dòng theo ngày, kể cả cảnh báo theo từng pha đã tắt từ trước) đã được gộp vào timeline và gỡ ngày 24/10/2026.

Bảng epic_milestone_history (mốc DESIGN_DONE/DEV_DONE/TEST_DONE, đã tắt ghi từ trước) đã được gỡ ngày 24/10/2026 — trạng thái hoàn thành từng pha của Epic đầy đủ tính live từ status Story/Subtask hiện tại mỗi lần tải trang.

10.2. Dòng thời gian cảnh báo theo đợt (epic_alert_timeline)

Bảng epic_alert_timeline theo dõi 5 loại cảnh báo của mỗi Epic dưới dạng các "đợt" (run) có khoảng ngày bắt đầu/kết thúc, cho phép biết chính xác Epic đã ở trạng thái cảnh báo đó liên tục từ ngày nào đến ngày nào, không chỉ ngày phát hiện:

  • FAIL_TTM_CNTT — Fail TTM-CNTT tổng thể (mục 8.3)
  • LATE_TTM_CNTT — Cảnh báo muộn TTM-CNTT theo trạng thái hiện tại (mục 8.2)
  • FAIL_TTM_E2E — Fail TTM-E2E (mục 8.3)
  • MISSING_START_DATE — Epic thiếu Start Date
  • DATA_ANOMALY — Dữ liệu bất thường (mục 9)

Mỗi lần aggregateBatchData() chạy (import thủ công, import tự động qua API, hoặc "Chạy lại" lớp dữ liệu), hệ thống tính lại cả 5 trạng thái này cho từng Epic bằng đúng những hàm dùng chung mà các màn hình giám sát dùng để hiển thị hôm nay (kết quả của Epic Scoring Service: hasDataAnomaly, Fail TTM-E2E, …) — nên lịch sử ghi lại không bao giờ "lệch pha" so với những gì màn hình đang hiển thị. So sánh với các "đợt" đang mở trong DB: đợt đang mở và vẫn còn đúng → nối dài thêm; đợt đang mở nhưng hết đúng → đóng lại (gán end_date); trạng thái mới xuất hiện → mở đợt mới. Toàn bộ thao tác ghi trong 1 lần import được gộp thành tối đa 3 câu lệnh SQL theo lô, không ghi từng Epic một. Dữ liệu này phục vụ mục "Dòng thời gian cảnh báo" trong popup Epic History ở màn hình Quản trị Epic (đầy đủ).

11.2. Quản trị Epic (đầy đủ) (/epic-alerts-15) — mọi role đã đăng nhập

Theo dõi chuyên sâu theo 5 pha mốc thời gian: Design (20%), Dev (50%), Test (80%), Pentest (90%), R4Golive (100%). Ngày baseline mỗi pha được tính tự động dựa trên số ngày làm việc tích lũy từ Start Date (T1); cột Release lấy baseline từ T0 + tiêu chí TTM-E2E, độc lập với Start Date. Trên sidebar, mục này chỉ hiển thị nhãn ngắn "Quản trị Epic" (không còn hậu tố "(đầy đủ)").

Quy tắc lọc trạng thái mặc định: Bộ lọc Status trên thanh công cụ luôn mặc định tích chọn (checked) tất cả các trạng thái ngoại trừ Cancelled, đảm bảo các Epic đã bị huỷ mặc định không xuất hiện khi truy cập màn hình này hay ở tất cả các danh sách route liên kết từ màn hình khác (người dùng vẫn có thể tích chọn Cancelled thủ công nếu có nhu cầu tra cứu).

Thứ tự nhóm trong bảng (từ 28/09/2026): Epic thông thường hiển thị trước, sau đó lần lượt là nhóm In PO → To Do → nhóm Epic có Nhận xét “Ngoài phạm vi TTM-CNTT” (bất kể status) → Released ở cuối. Trong mỗi nhóm vẫn giữ thứ tự cũ: Epic sai lệch dữ liệu xuống cuối nhóm, rồi theo mức cảnh báo (FAIL → LATE → EARLY → NONE) và số ngày làm việc còn lại.

Widget trên banner (từ 30/09/2026): TTM-CNTT (QLDA) và TTM-CNTT (QA), tính trên đúng các Epic của bảng Danh sách Epic đang lọc (mọi bộ lọc trên thanh công cụ và Advanced Filters) — đổi bộ lọc thì chỉ số đổi theo. Hai widget toàn ứng dụng (QLDA) đã bỏ khỏi màn này — riêng từ 01/10/2026, có thêm 1 widget thứ 3 cố định TTM-E2E (toàn công ty, đọc từ cache ttm_index_global_cache, giống nhau với mọi người dùng, không đổi theo bộ lọc — xem mục 11.5).

Điều chỉnh 08/10/2026: bỏ ngoại lệ "R4G Date ở tương lai là ngày kế hoạch" (áp dụng 05/10–08/10): Epic có R4G Date mà status chưa tới R4GOLIVE là Sai lệch dữ liệu (R8) kể cả khi ngày đó chưa tới — R4G Date là ngày thực tế đạt R4GOLIVE (pha R4GOLIVE "Hoàn thành", L04a "Epic hoàn thành" và trục Release đều đọc theo nghĩa này).

Bổ sung 09/10/2026 — quy định của công ty: R4G Date không được khai báo trước. Mọi Epic có R4G Date còn ở tương lai là Sai lệch dữ liệu, chỉ trừ Cancelled: status chưa tới R4GOLIVE là R8, status từ R4GOLIVE trở lên hoặc Reopened là R10 "R4G Date ở tương lai" (mới, scoring-12 — trước đó nhóm này là "chưa kết luận" L05ac). Epic owner cần xoá giá trị khỏi trường R4G Date và ghi ngày dự kiến ở một trường thông tin phụ khác. Vì Sai lệch dữ liệu được xét trước kết luận TTM, Epic đó không được chấm Đạt / Fail và nằm ngoài mẫu số TTM-CNTT / TTM-E2E cho tới khi sửa — kể cả khi R4G Date khai báo trước muộn hơn Target, hoặc Epic đang Fail vì quá Target chưa có R4G Date (xoá R4G Date thì Epic trở lại Fail).

Điều chỉnh 05/10/2026: R8 áp dụng cả với status được miễn các rule khác (To Do / In PO / Backlog), chỉ trừ Cancelled; R9 chỉ xét status R4GOLIVE / MVP Done / Pilot / Done / Released (status lạ, Pending, Reopened không bị bắt).

Quy tắc chấm điểm (Scoring Service, từ 01/10/2026): Sai lệch dữ liệu được xét trước — Epic có Sai lệch dữ liệu (R1, R3–R6; từ 04/10/2026 thêm R8 "có R4G Date nhưng status < R4GOLIVE" và R9 "status ≥ R4GOLIVE nhưng thiếu R4G Date", R1 tính từ status DESIGN, R5 chỉ tính khi status đã qua DESIGN) không được chấm Đạt / Fail / Cảnh báo muộn / Sai Status trên TTM-CNTT (QLDA), TTM-CNTT (QA) và TTM-E2E cho tới khi dữ liệu được sửa. Epic có ngày ghi nhận đúng hạn nhưng status chưa lên R4GOLIVE vẫn được tính Đạt và hiện kèm badge “Sai Status”. TTM-E2E: hạn = T0 + (N − 1) ngày làm việc, Đạt không còn yêu cầu status Released. Xem popup “Logic cảnh báo” để biết công thức từng badge.

Bộ lọc Nhận xét: ngoài các giá trị Đạt/Fail/Cảnh báo/Sai Status/Sai lệch dữ liệu/trục Release, có thêm lựa chọn “Ngoài phạm vi TTM-CNTT” để lọc riêng các Epic nằm ngoài khoảng ngày “R4G for TTM (CNTT)” đang cấu hình (mục 8.7).

11.4. Chuẩn hoá dữ liệu (/data-normalization) — từ 12/10/2026

Menu "Giám sát", ngay dưới Quản trị Epic (chức năng data_normalization trong Ma trận phân quyền). Liệt kê các Epic cần sửa dữ liệu trên Jira, mỗi rule một panel (mặc định đóng, bấm tiêu đề để mở; tiêu đề luôn hiện số Epic):

  1. Thiếu lý do Fail TTM — Epic Fail TTM-CNTT có R4G Date muộn hơn Target mà chưa ghi khâu fail hoặc chưa có phòng chịu trách nhiệm chính; đúng tập Epic của widget THIẾU LÝ DO trên TTM Dashboard 2 (chỉ có ở engine Scoring Service).
  2. R1, R3–R6, R7 "Sai Status (Release)", R8–R10 — theo thứ tự R. Phụ đề là giải thích rule và "Cách chuẩn hoá" (lấy từ khuyến nghị tương ứng của Scoring Service). R8–R10 chỉ có khi engine hiển thị là Scoring Service; ở engine cũ R1/R5/R7 hiện đúng điều kiện của engine cũ. R2 "Pending lâu" không có panel.

Một Epic có thể nằm ở nhiều panel. Dữ liệu theo phạm vi quyền của người xem và cùng bộ lọc với TTM Dashboard 2 (Domain, Dự án, Component, PM/SM, Đơn vị yêu cầu); Epic Cancelled và Epic ngoại lệ không xuất hiện. Bảng Epic: key + Summary, Created date, Ngày duyệt ý tưởng, Start date, R4G date, Due date, Status; 25 Epic/trang.

11.6. Báo cáo Epic (/reports) — mọi role đã đăng nhập

Màn hình báo cáo theo từng dự án (không gộp nhiều dự án như Dashboard) — đây là mục đầu tiên trong nhóm "Giám sát" trên sidebar. Người dùng chọn 1 Dự án, tùy chọn lọc thêm Domain/Component/khoảng ngày, và chọn 1 ngày trong các ngày được giữ chi tiết (30 ngày import gần nhất và ngày làm việc cuối mỗi tuần) để xem trạng thái của mọi Epic tại ngày đó. Dùng lại đúng engine tính cảnh báo/tuân thủ/sai lệch dữ liệu (Epic Scoring Service, scoreEpic) với 3 màn hình giám sát Epic ở trên — không tính lại bằng công thức riêng.

Kết quả gộp Epic của dự án vào 6 danh sách:

  1. Epic đã Released trong giai đoạn lựa chọn.
  2. Epic Đạt TTM-CNTT và TTM-E2E.
  3. Epic Fail TTM-CNTT và TTM-E2E.
  4. Epic In PO (To Do, In PO).
  5. Epic có Sai lệch dữ liệu.
  6. Epic Pending.

Mỗi dòng Epic có thể bấm mã để mở popup Duyệt Epic hoặc mở thẳng Jira ở tab mới. Đây cũng là báo cáo duy nhất được expose sẵn cho AI chatbot qua MCP Server (tool list_report_filters, mục 16).

12. Màn hình Nguồn dữ liệu (/)

Có 4 tab, chuyển bằng thanh tab ở đầu trang: Import Issues (nội dung chính, SUPERADMIN), Quản lý Component (dọn dẹp danh mục Component, SUPERADMIN) Từ chối import (danh sách Epic không được import, SUPERADMIN) và Dọn lịch sử (công tắc, giới hạn và xem trước / dọn tay việc xoá lịch sử issues — mục 6.5, SUPERADMIN).

12.1. Tab Import Issues

  • Thiết lập nguồn dữ liệu CSV — chọn file, kiểm tra lỗi hoặc import & lưu.
  • Nhật ký lịch sử import (Lớp Dữ liệu) — danh sách batch, xem chi tiết lỗi/cảnh báo (nay có cả cờ WARNING cho dữ liệu bất thường, xem mục 9), duyệt dữ liệu, xoá batch.
  • Nhật ký lớp dữ liệu tổng hợp (Epic) (SUPERADMIN) — quản lý riêng 4 bảng tổng hợp/hậu-tổng hợp theo ngày (hỗ trợ Xóa và Chạy lại).
  • Xoá N lớp dữ liệu gần nhất (SUPERADMIN) — xoá cả raw lẫn tổng hợp của N ngày gần nhất, có preview trước khi xác nhận (mục 6.3).
  • Nhật ký lịch sử import có cột Từ chối (số dòng bị loại bởi Từ chối import, không tính vào Tổng dòng — mục 3.4).
  • Cấu hình Đợt Import (right panel) — loại nguồn, định dạng file (adapter), thời gian tổng hợp (nhận diện tự động từ tên file theo mẫu Jira YYYY-MM-DDThh_mm_ss+0700.csv).
  • Lưu trữ dữ liệu import (right panel, SUPERADMIN) — cấu hình số ngày giữ raw data.
Hoàn thiện dữ liệu (bổ sung/vá dữ liệu còn thiếu cho issue đã import, chạy lại tổng hợp) — code vẫn còn nguyên nhưng box này đang tạm ẩn khỏi màn hình theo yêu cầu, chưa dùng lại được từ UI.

12.2. Tab Quản lý Component

Không phải màn hình import — đây là công cụ dọn dẹp danh mục project_components, vốn chỉ tích luỹ dần theo dữ liệu Component đọc được từ mỗi issue import (chưa từng có cơ chế nào tự xoá bớt). Liệt kê các Component "mồ côi": có trong danh mục nhưng không còn xuất hiện trên dữ liệu mới nhất của bất kỳ issue nào đã import (ví dụ Component đã đổi tên/xoá trên Jira). Hỗ trợ thêm/sửa/xoá thủ công 1 Component (chọn Dự án, nhập tên Component, bật/tắt Active) — chỉ SUPERADMIN, tab tự ẩn nội dung nếu gọi API mà bị 401/403.

12.3. Tab Từ chối import (từ 14/10/2026)

Quản lý danh sách Epic không được import (mục 3.4) — chỉ SUPERADMIN. Gồm 3 khối:

  • Rule tự động — trên 1 dòng: Ngày Created >= (ngày A) và Ngày Due Date >= (ngày B; Epic Released / MVP Done trống Due Date thì xét R4G Date), nút Lưu cấu hình và Quét lại CSDL (liệt kê Epic đang có trong CSDL vi phạm rule để chọn từ chối).
  • Thêm Epic vào danh sách từ chối import — trên 1 dòng: ô Epic key (dán nhiều key, cách nhau bởi dấu phẩy/khoảng trắng/xuống dòng), ô Lý do, nút Thêm vào danh sách (popup cảnh báo xem trước số issue/dòng sẽ xóa, đồng ý thì Epic được thêm và chạy Epic deletion).
  • Danh sách Epic từ chối import — ô tìm kiếm và thao tác theo lô trên các dòng đã chọn: Cho phép import, Từ chối lại, Xóa theo lô, Xóa dữ liệu còn tồn tại (cho Epic bị từ chối mà CSDL vẫn còn dữ liệu, ví dụ sau khi chạy migration trên CSDL khác). Bảng tự co theo nội dung, không cần cuộn ngang (Summary / Đơn vị yêu cầu cắt bớt, rê chuột xem đủ): Epic, Summary, Status, Đơn vị yêu cầu, Created, Duyệt ý tưởng, Start, R4G, Due, Nguồn (rê chuột lên badge để xem lý do), Cho phép import (bật/tắt; tắt = từ chối lại và xóa dữ liệu), Dữ liệu CSDL (Còn / Đã xóa), xóa khỏi danh sách.
  • Mỗi lần xóa dữ liệu hiện toast nhắc chạy lại cache thủ công.
  • Job dọn hằng ngày tự ghi “Miễn rule B” cho các Epic đang được miễn rule B nhờ lịch sử trong CSDL (kể cả Epic không còn xuất hiện trong file import), chạy trước bước dọn lịch sử, để bằng chứng không mất khi lịch sử bị tỉa / hết hạn lưu trữ. Bằng chứng được tính theo cả khoảng thời gian phiên bản “chưa Released” còn hiệu lực (từ 26/10/2026).

16. MCP Server — kết nối AI chatbot

Cho phép người dùng kết nối AI chatbot (Claude, ChatGPT, Gemini, Copilot...) trực tiếp tới TTM Monitor qua giao thức MCP (Model Context Protocol) để tra cứu dữ liệu bằng hội thoại thay vì vào giao diện. Mọi tool MCP đều gọi lại đúng service layer đang phục vụ UI (không truy vấn CSDL riêng), nên kết quả trả về cho AI chatbot luôn tôn trọng đúng RBAC hiện có của người dùng đang kết nối.

16.1. Bật/tắt & endpoint

  • Công tắc mcp_settings.is_enabled (bảng singleton) — cấu hình tại sidebar Quản trị hệ thống → tab MCP Server, chỉ SUPERADMIN. Tắt là chặn toàn bộ truy cập MCP ngay lập tức, kể cả token còn hiệu lực.
  • Endpoint duy nhất: /api/mcp (GET/POST/DELETE) — dựng bằng WebStandardStreamableHTTPServerTransport, tạo mới hoàn toàn cho mỗi request (stateless, không giữ session giữa các lần gọi) vì hạ tầng serverless không giữ tiến trình sống liên tục.
  • 2 endpoint .well-known (oauth-protected-resource, oauth-authorization-server) công bố metadata OAuth cho client tự động dò cấu hình kết nối.

16.2. Xác thực — 2 cách

CáchCơ chế
Personal Access Token (PAT)Người dùng tự tạo tại menu avatar → Thông tin cá nhân, đặt tên gợi nhớ; giá trị token thật (tiền tố ttm_mcp_) chỉ hiển thị đúng 1 lần lúc tạo (bảng chỉ lưu bản băm SHA-256). Có thể thu hồi bất kỳ lúc nào. Dùng header Authorization: Bearer <token>.

17. SSO & API Key — đăng nhập liên kết ứng dụng khác

Đây là chiều ngược lại với việc TTM Monitor đăng nhập qua AD Server/Keycloak (vẫn là hạng mục roadmap tương lai) — ở đây TTM Monitor đóng vai trò nhà cung cấp SSO (Identity Provider) cho một ứng dụng nội bộ khác: cho phép ứng dụng đó lấy thông tin (email, họ tên, role) của user đang đăng nhập TTM Monitor mà không cần user đăng nhập lại lần hai.

17.1. API Key (client_id)

SUPERADMIN cấp tại sidebar Quản trị hệ thống → tab Quản lý API key: mỗi key gồm tên gợi nhớ, tên ứng dụng, chuỗi api_key (dùng làm client_id), cờ Đang hoạt động, cờ "Không giới hạn" hoặc khoảng ngày hiệu lực (valid_from/valid_to).

17.2. Luồng Authorization Code (5 phút)

  1. Ứng dụng ngoài điều hướng user tới /sso/authorize?client_id=<api_key>&redirect_uri=<url> trên TTM Monitor.
  2. Trang tự kiểm tra client_id hợp lệ (GET /api/sso/verify-client) và user đã đăng nhập TTM Monitor hay chưa (GET /api/auth/me); nếu chưa đăng nhập sẽ yêu cầu đăng nhập trước.
  3. User xác nhận, hệ thống gọi POST /api/sso/authorize, sinh 1 mã dùng-một-lần (sso_auth_codes.code, hết hạn sau 5 phút) rồi điều hướng về đúng redirect_uri kèm mã này (và state nếu có).
  4. Ứng dụng ngoài đổi mã lấy hồ sơ user bằng POST /api/sso/token (body code + api_key, hoặc header X-API-Key) — trả về appName và user (id, email, họ tên, role). Mã chỉ đổi được đúng 1 lần; đổi lại lần 2 báo lỗi CODE_ALREADY_USED.
Trường accessToken trong phản hồi /api/sso/token chỉ là chuỗi định danh tham khảo (ghép từ timestamp + user id), không phải một token có thể xác minh lại được ở phía TTM Monitor — ứng dụng ngoài cần tự quản lý phiên đăng nhập của họ sau khi nhận được hồ sơ user, không dùng lại chuỗi này như một bearer token.

Trang /sso-demo (kèm /api/sso-demo/callback) minh hoạ đầy đủ luồng trên từ phía một ứng dụng khách mẫu.

18. Visit Counter — Thống kê lượt truy cập & tương tác người dùng

Visit Counter là phân hệ đo lường, theo dõi và phân tích tần suất sử dụng cũng như lưu lượng truy cập của người dùng trên toàn bộ hệ thống TTM Monitor. Tính năng ghi nhận chi tiết lượt đăng nhập vào ứng dụng và lượt xem tại 4 màn hình nghiệp vụ trọng điểm, từ đó tổng hợp số liệu đa chiều phục vụ công tác giám sát vận hành và đánh giá mức độ tương tác của các Domain và người dùng.

18.1. Cơ chế thu thập sự kiện & 3 màn hình trọng điểm

Hệ thống tự động ghi nhận nhật ký vào bảng CSDL visit_logs qua 2 loại sự kiện chính:

  • Lượt truy cập ứng dụng (event_type = 'APP_LOGIN'): Được ghi nhận tự động mỗi khi một người dùng đăng nhập thành công vào hệ thống (thực hiện tại auth-service.ts khi tạo phiên làm việc). Sự kiện này gắn với mã người dùng (user_id), cho biết tần suất đăng nhập thực tế của từng tài khoản.
  • Lượt truy cập màn hình trọng điểm (event_type = 'SCREEN_VIEW'): Hệ thống chủ động đo lường lưu lượng trên 3 màn hình nghiệp vụ trọng tâm (hai màn hình cũ TTM Dashboard và Epic in PO đã gỡ, chỉ còn lịch sử):
    1. TTM Dashboard (/dashboard-new, đã gỡ 11/10/2026) — screen_key = 'dashboard': chỉ còn lịch sử lượt xem cũ, không còn ghi nhận mới.
    2. Quản trị Epic (/epic-alerts-15) — screen_key = 'epic_alerts': Màn hình theo dõi tiến độ chi tiết 5 pha của các Epic.
    3. Báo cáo Epic (/reports) — screen_key = 'epic_reports': Màn hình trích xuất báo cáo chuyên sâu theo từng dự án và lớp dữ liệu.
    4. Epic in PO (đã gỡ 11/10/2026) — screen_key = 'epic_in_po': chỉ còn lịch sử lượt xem cũ, không còn ghi nhận mới.
Cơ chế chống đếm lặp (Client-side Debouncing): Để tránh việc ghi nhận trùng lặp khi người dùng chuyển đổi tab liên tục hoặc component re-render, phía client (src/lib/visit-counter-client.ts) duy trì cờ thời gian trong sessionStorage với ngưỡng debounce 30 giây cho từng màn hình. Nếu người dùng xem lại cùng một màn hình trong vòng 30 giây của cùng phiên trình duyệt, request ghi nhận sẽ được bỏ qua.

18.2. Khái niệm chu kỳ thời gian & Thống kê đa chiều

Số liệu từ bảng visit_logs được phân tích theo các khung thời gian và góc nhìn quản trị:

Khung thời gian trượt

• Hôm nay ($T$): Tính từ đầu ngày hiện tại (00:00:00) theo giờ địa phương.
• Tuần này ($T-7 \to T$): Cửa sổ trượt 8 ngày gần nhất, phản ánh lưu lượng tương tác hiện thời.
• Tuần trước ($T-15 \to T-8$): Cửa sổ 8 ngày đối ứng liền trước, dùng làm mốc so sánh tăng trưởng.
• Tổng số (Lũy kế): Toàn bộ dữ liệu tích lũy từ khi hệ thống bắt đầu ghi log.

Phân tích đa chiều

• Theo Domain nghiệp vụ: Tổng hợp số lượng user active và tổng lượt truy cập phân theo từng Domain.
• Theo từng User: Tần suất đăng nhập và sử dụng của từng tài khoản cụ thể.
• Theo thời gian: Phân rã số liệu theo tuần, theo ngày (trend line 7 ngày), và theo giờ.
• Theo màn hình: So sánh mức độ quan tâm giữa 3 màn hình trọng điểm.

18.3. Vị trí hiển thị trên giao diện người dùng

19. Tech stack

Tổng quan công nghệ nền của hệ thống — quy trình nghiệp vụ Import/ETL đã mô tả chi tiết ở mục 3, mục này chỉ nêu lớp công nghệ/hạ tầng bên dưới.

Frontend

Next.js 16 (App Router, React 19) + TypeScript, Tailwind CSS 4. Toàn bộ màn hình là Client Component ('use client'), gọi thẳng các Route Handler nội bộ qua fetch, không dùng thư viện quản lý state/data-fetching riêng (React state + useMemo).

Backend

Next.js Route Handlers (src/app/api/**/route.ts) chạy trên Node.js — vừa là API vừa là nơi phục vụ giao diện (không có server Express/NestJS riêng). Truy vấn CSDL bằng SQL thuần qua driver pg (node-postgres), không dùng ORM.

Xác thực

Tự xây (không dùng NextAuth/Clerk…): mật khẩu băm bằng bcrypt, phiên đăng nhập lưu ở bảng auth_sessions (token băm, có hạn dùng 2 giờ hoặc 24 giờ nếu "Ghi nhớ đăng nhập"), gắn vào cookie HTTP-only phía trình duyệt. Phân quyền RBAC theo 4 role cố định (mục 2), kiểm tra ở từng Route Handler qua hàm dùng chung requireUser().

Cơ sở dữ liệu

PostgreSQL, chạy song song 2 profile kết nối (local / Supabase — Aiven đã ngừng sử dụng từ 26/09/2026) chọn qua biến môi trường DB_CONNECTION. Schema quản lý bằng migration có đánh version trong db/migrations, áp dụng thủ công cho từng profile qua script scripts/migrate-db.js — không tự động chạy migration khi deploy.

21.3. Tỷ lệ % Pass / % Fail TTM-CNTT

Tỷ lệ % Pass TTM-CNTT = L05aa / (L05aa + L05ab + L05ba) × 100
Tỷ lệ % Fail TTM-CNTT = (L05ab + L05ba) / (L05aa + L05ab + L05ba) × 100
  • Mẫu số chỉ gồm Epic đã có kết luận: Đạt (L05aa), không đạt nhóm 1 (L05ab), không đạt nhóm 2 (L05ba). Epic chưa kết luận (L05ac), Epic trong hạn (L05bb), Epic Cancelled, Epic ngoại lệ (Black listed + dự án Time to Market = N) và Epic Sai lệch dữ liệu không tham gia.
  • % Pass + % Fail = 100%. Khi chưa có Epic nào được kết luận (mẫu số = 0), mọi nơi hiển thị "—" (phễu, vòng chỉ số, badge banner, ô ma trận) thay cho 100% — quyết định 05/10/2026.
  • TTM-E2E dùng cùng công thức từ 05/10/2026: Đạt TTM-E2E / (Đạt TTM-E2E + Fail TTM-E2E).
  • Đây chính là công thức của chỉ số TTM-CNTT (QLDA) và TTM-CNTT (QA) trên mọi màn hình (mục 8.7) — nên tỷ lệ ở phễu luôn bằng chỉ số TTM-CNTT (QLDA) của cùng tập Epic.

21.9. Lead view cho tất cả user (từ 14/10/2026)

Công tắc "Dashboard Lead view cho tất cả user" ở Quản trị hệ thống → Dashboard (SUPERADMIN, bảng singleton dashboard_view_settings, mặc định bật). Khi bật, user có phạm vi dữ liệu hẹp hơn toàn công ty (Admin, PM/SM) mở TTM Dashboard 2 sẽ mặc định thấy màn hình của Lead với số liệu toàn công ty (bộ lọc Domain, đủ các section pie chart), và chuyển được về số liệu theo phạm vi của mình bằng nút Toàn công ty / Của tôi trên đầu trang — ở chế độ Của tôi mọi chức năng xem dashboard theo view của user giữ nguyên như trước (Admin vẫn có Lead / PM/SM và xem góc nhìn user khác).

  • Chỉ con số thống kê được mở rộng. Khi bấm vào số liệu để mở popup Quản trị Epic, danh sách vẫn theo đúng phân quyền dữ liệu của user, nên có thể ít hơn con số trên dashboard — màn hình hiện dòng ghi chú này khi đang ở Lead view.
  • Số liệu toàn công ty đọc từ cùng bộ cache ALL của SUPERADMIN/SUPERVISOR (mục 21.5). Khi lọc ở Lead view, số liệu được tính ở máy chủ — trình duyệt chỉ nhận con số tổng hợp, không nhận dòng Epic nào của toàn công ty (từ 19/10/2026).
  • SUPERADMIN / SUPERVISOR vốn đã xem toàn công ty nên không thấy nút chuyển. Tắt công tắc: mọi user quay về chỉ xem số liệu theo phạm vi của mình.
