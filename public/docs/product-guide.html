1. Tổng quan hệ thống

TTM Monitor theo dõi rủi ro Time to Market (TTM) của các Epic Jira: từ lúc bắt đầu triển khai (Start Date / T1) tới khi lên môi trường sản xuất (R4G Date), so với mốc chuẩn cấu hình theo Loại Epic và trạng thái. Dữ liệu được nạp định kỳ từ file CSV export từ Jira; hệ thống tự tính toán cảnh báo và hiển thị trên các màn hình giám sát.

Đối tượng dùng chính

PM/SM theo dõi Epic phụ trách, Lead theo dõi Domain, CBQL Phòng theo dõi toàn bộ; Admin/SUPERADMIN cấu hình hệ thống.

Nguồn dữ liệu

File CSV export chuẩn từ Jira, import thủ công theo lớp dữ liệu hàng ngày (data layering theo aggregated_at).

Phạm vi cảnh báo

TTM-CNTT (từ Start Date tới R4G) là trọng tâm; TTM-E2E (từ ngày duyệt ý tưởng tới Release) theo dõi song song.

Nguyên tắc tính toán

Mọi cảnh báo tính bằng ngày làm việc (bỏ Thứ Bảy/Chủ Nhật/ngày nghỉ cấu hình), tính lại theo thời gian thực mỗi lần tải màn hình.

Epic không gắn Component nào luôn hiển thị cho mọi user được phân quyền dự án đó, bất kể có cấu hình Component hay không.
Khối dữ liệu

3. Quy trình Import dữ liệu

Thực hiện tại màn hình Nguồn dữ liệu (route /). Mỗi lần import tạo một lớp dữ liệu gắn với một mốc thời gian tổng hợp (aggregated_at).

3.1. Mô hình import theo ngày (incremental)

File CSV hàng ngày chỉ chứa các issue có trường updated rơi vào đúng ngày import đó — không phải bản snapshot đầy đủ toàn bộ dữ liệu. Vì vậy hệ thống không dựa vào "batch mới nhất" để hiển thị, mà luôn lấy dòng dữ liệu mới nhất của từng Epic trong toàn bộ lịch sử tích lũy.

3.2. Các bước xử lý khi import (không ở chế độ "chỉ kiểm tra lỗi")

  1. Parse CSV, chuẩn hoá thành các issue thô.
  2. Validate từng dòng: VALID / WARNING / INVALID. Nếu có dòng INVALID, cả batch coi là FAILED và không ghi vào bảng canonical.
  3. Lưu toàn bộ dòng thô vào import_rows (kèm kết quả validate).
  4. Ghi/UPSERT vào bảng canonical issues (1 dòng / issue / batch).
  5. Liên kết quan hệ Subtask → Story → Epic trong phạm vi batch.
  6. Chạy aggregateBatchData(): tính lại 4 lớp dữ liệu tổng hợp/hậu-tổng hợp (mục 4).
  7. Dọn dữ liệu raw quá hạn lưu trữ (theo cấu hình retention), luôn bảo toàn batch mới nhất.
Chế độ “Chỉ kiểm tra lỗi” (Validate only) chỉ chạy bước 1–2, không ghi gì vào CSDL — dùng để rà soát file trước khi import thật.

3.3. API import tự động (script Python)

Bên cạnh form upload thủ công (session + SUPERADMIN), hệ thống có 1 endpoint riêng để 1 script Python gọi trực tiếp ngay sau khi export xong CSV từ Jira: POST /api/data-source/import/auto.

Thuộc tínhGiá trị
Xác thựcHeader Authorization: Bearer <token> — token tĩnh cấu hình qua biến môi trường IMPORT_API_TOKEN trên server (không phải session người dùng), so khớp bằng thuật toán constant-time. Sai/thiếu token → 401; server chưa cấu hình token → 503.
Payloadmultipart/form-data với field file — cùng định dạng CSV (adapter Py Jira API cố định, không truyền được adapter khác), giới hạn 2MB (thoải mái hơn nhiều so với <500KB script thường xuất ra).
Thời điểm tổng hợpaggregatedAt luôn = thời điểm server nhận request (không nhận tham số từ script) — đúng ngữ nghĩa "vừa export xong, import ngay bây giờ".
Pipeline xử lýGọi lại đúng processImport() dùng chung với form thủ công — cùng bước validate → import_rows → issues → aggregateBatchData() → dọn dữ liệu quá hạn (mục 3.2). Không có chế độ "chỉ kiểm tra lỗi" ở API này.
Truy vếtBatch tạo ra được đánh dấu nguồn AUTO, người thực hiện hiển thị "Python Script (Auto Import)" trong Nhật ký lịch sử import — phân biệt rõ với batch import thủ công qua UI.
Phản hồiTrả về cùng cấu trúc JSON kết quả import (status, totalRows/successRows/warningRows/errorRows, …) như API import qua UI — script có thể tự xác định thành công/thất bại theo status/mã HTTP mà không cần đăng nhập giao diện.
Endpoint này được liệt kê riêng trong danh sách route công khai (không qua kiểm tra session đăng nhập của lớp middleware nội bộ) — hệ thống middleware của ứng dụng chỉ hiểu xác thực bằng session, nên mọi route dùng bearer token đều phải khai báo tường minh để không bị chặn 401 trước khi vào tới route handler.

5. Vòng đời & lưu trữ dữ liệu

5.1. Lưu trữ dữ liệu import (raw)

Cấu hình tại panel “Lưu trữ dữ liệu import” (right panel màn hình Nguồn dữ liệu, SUPERADMIN): số ngày giữ dữ liệu raw (import_batches/import_rows/issues), mặc định 30 ngày, tối thiểu 7. Sau mỗi lần import thành công, hệ thống tự dọn các batch cũ hơn ngưỡng — batch mới nhất luôn được bảo vệ để tránh mất nguồn cảnh báo hiện hành.

5.2. Quản lý lớp dữ liệu tổng hợp

Panel “Nhật ký lớp dữ liệu tổng hợp (Epic)” (cùng màn hình Nguồn dữ liệu, chỉ SUPERADMIN) liệt kê từng ngày có dữ liệu tổng hợp, kèm số dòng ở mỗi bảng và trạng thái dữ liệu import gốc (còn/đã dọn). Hai hành động:

  • Xoá — chỉ xoá 4 bảng tổng hợp/hậu-tổng hợp của ngày đó (mục 4.1), không đụng tới dữ liệu import gốc.
  • Chạy lại — tính lại tổng hợp từ dữ liệu issues hiện có (không cần import lại CSV); chỉ khả dụng khi raw của ngày đó còn tồn tại.
Nếu dữ liệu raw của một ngày đã bị dọn theo retention, nút "Chạy lại" cho ngày đó sẽ không khả dụng — lớp tổng hợp đã có vẫn được giữ nguyên, chỉ không thể tái tạo lại từ đầu.

5.3. Xoá N lớp dữ liệu gần nhất

Thao tác riêng biệt (cùng màn hình, chỉ SUPERADMIN), mạnh hơn "Xoá" ở mục 5.2: xoá cả raw lẫn tổng hợp của N "lớp dữ liệu" gần nhất, trong đó một lớp dữ liệu là một ngày bất kỳ có dữ liệu ở bất kỳ bảng nào trong chuỗi xử lý (raw hoặc tổng hợp). Có bước xem trước (preview) số dòng sẽ bị xoá ở từng bảng trước khi xác nhận. Dùng khi cần loại bỏ hẳn một đợt dữ liệu lỗi, khác với "Xoá"/"Chạy lại" vốn chỉ tác động tới lớp tổng hợp.

6. Cấu hình chính sách TTM & rule cảnh báo

Tại màn hình Cấu hình cảnh báo (/admin/status-alert-rules) có 2 nhóm cấu hình độc lập:

6.1. Tiêu chí Time to Market (TTM Policy)

Xác định deadline tổng thể: Target = From TTM Field + số ngày làm việc, theo từng cặp (Loại TTM × Loại Epic). From TTM Field/To TTM Field là nhãn logic nội bộ ứng dụng (Start Date, Idea Approved Date, R4G Date, Due Date) — không phải tên cột trong file CSV import gốc. Loại TTM gồm TTM-CNTT (T1 → R4G, trọng tâm MVP1) và TTM-E2E (T0 → Release).

6.2. Rule cảnh báo theo trạng thái Epic (epic_status_alert_rules)

Với mỗi cặp (Loại Epic × Trạng thái Epic), cấu hình 2 mốc: Cảnh báo sớm, Cảnh báo muộn — tính bằng số ngày làm việc kể từ T1. Mốc Fail TTM-CNTT không còn nằm ở bảng này (cột fail_offset_days đã bị bỏ) — Fail TTM-CNTT/ TTM-E2E lấy hoàn toàn từ Tiêu chí Time to Market ở mục 6.1. Design và In Progress là dữ liệu seed mặc định; có thể thêm rule cho trạng thái khác (IN PO, DEV, TEST, PENTEST, R4GOLIVE, MVPDONE, Released…).

Trạng thái EpicEpic đơn giản (TTM-CNTT 15 ngày)Epic phức tạp (TTM-CNTT 30 ngày)
DesignSớm: T1+2 · Muộn: T1+3Sớm: T1+5 · Muộn: T1+6
In ProgressSớm: T1+12 · Muộn: T1+13Sớm: T1+19 · Muộn: T1+20

6.3. Phân loại độ phức tạp Epic (SIMPLE / COMPLEX)

Mọi mốc cảnh báo ở trên phụ thuộc Epic là đơn giản (SIMPLE) hay phức tạp (COMPLEX) — tính tự động mỗi lần import, dựa trên 2 trường Jira của Epic, không cấu hình thủ công:

  • Epic được xếp SIMPLE khi đồng thời thoả cả 2 điều kiện: Loại yêu cầu (request type) là rỗng, "none", "cải tiến" hoặc "tính năng mới" và Requirement Level là rỗng, "none", "1" hoặc "2" (so khớp không phân biệt hoa/thường và khoảng trắng thừa).
  • Mọi tổ hợp còn lại (kể cả khi chỉ 1 trong 2 điều kiện không thoả) được xếp COMPLEX.
Nói cách khác: mặc định (thiếu dữ liệu 1 hoặc cả 2 trường) Epic được coi là SIMPLE; Epic chỉ "rớt" xuống COMPLEX khi có ít nhất một trong hai trường mang giá trị vượt ngoài các mức thấp/nhẹ liệt kê ở trên (ví dụ Loại yêu cầu = "dự án mới", hoặc Requirement Level = "3" trở lên).

7. Logic tính cảnh báo Epic (TTM-CNTT & TTM-E2E)

7.1. Thứ tự trạng thái chuẩn (STATUS_ORDER)

TO DO → IN PO → DESIGN → DEV → TEST → PENTEST → R4GOLIVE → MVPDONE → RELEASED

Trường R4G Date trên Epic tương ứng với ngày hoàn thành trạng thái R4GOLIVE. Trạng thái không khớp danh sách này (kể cả Cancelled) được xếp sau cùng. Jira status legacy In Progress/In Dev chuẩn hóa thành DEV; Pen Test thành PENTEST; Ready For Golive thành R4GOLIVE.

7.2. Cột trạng thái/pha trên bảng Epic Alerts

Màn hình rút gọn có 3 cột (Design, In Progress, Ready4Golive); màn hình đầy đủ/Epic in PO có 5 cột pha (DESIGN/DEV/TEST/PENTEST/R4GOLIVE). Mỗi cột so sánh vị trí trạng thái hiện tại của Epic với vị trí trạng thái của cột đó:

RuleĐiều kiệnHiển thị
TTM-CNTT-1today < mốc sớm và Epic ở trạng thái trước cột“Target: dd/mm/yyyy”
TTM-CNTT-2Trước/giữa 2 mốc, Epic đang đúng trạng thái cột“Target: dd/mm/yyyy”
TTM-CNTT-3Đúng ngày mốc sớm, Epic đang đúng trạng thái cộtCảnh báo sớm
TTM-CNTT-4/5Từ ngày mốc muộn trở đi, Epic đang đúng trạng thái cộtCảnh báo muộn
TTM-CNTT-6Epic đã đi qua trạng thái cột (bất kể ngày)Icon hoàn thành (Pass) — riêng cột Ready4Golive hiện luôn ngày R4G Date thực tế nếu có
Mở rộng an toàn: nếu Epic chưa tới trạng thái cột nhưng đã qua mốc sớm → nhãn đổi thành “Past target”; nếu Epic đã qua trạng thái cột nhưng chưa tới mốc muộn → vẫn coi là hoàn thành (Pass), vì trạng thái đã đi qua thì luôn là “đã xong”. Cuối mỗi bảng có chú giải màu nền Done (xanh)/Warning (vàng)/Failed (đỏ) dùng chung cho các ô này.

7.3. Cột "Nhận xét" — 2 badge cảnh báo tổng thể độc lập

Fail TTM-CNTT: so sánh R4G Date (hoặc ngày hiện tại nếu chưa có) với Target tổng theo tiêu chí TTM-CNTT (mục 6.1). Badge “Đạt TTM” xuất hiện khi Epic đã có R4G Date và không bị cảnh báo.

Fail TTM-E2E (badge riêng, độc lập hoàn toàn với Fail TTM-CNTT): chỉ có FAIL/NONE, không có mức Cảnh báo sớm/muộn. Tính từ T0 (Idea Approved Date, tự fallback sang ngày tạo Epic trên Jira nếu thiếu) tới Due Date (hoặc hôm nay nếu chưa có), so với tiêu chí TTM-E2E. Vì T0 luôn tính được, cột stripe TTM-E2E và badge này hiển thị đầy đủ ở cả 3 màn hình giám sát kể cả khi Epic thiếu Start Date.

7.4. Nguyên tắc tính real-time

Không màn hình Epic Alerts nào đọc dữ liệu đã tổng hợp sẵn. Mỗi lần tải trang, hệ thống lấy dòng issues mới nhất của từng Epic (không giới hạn theo 1 batch cụ thể) và tính lại toàn bộ cảnh báo — cả TTM-CNTT lẫn TTM-E2E — tại đúng thời điểm request, theo rule đang active. Vì vậy nếu không import gì trong ngày, cảnh báo vẫn có thể tự chuyển trạng thái theo ngày thực tế.

7.5. Cách tính ngày baseline từng pha (màn hình đầy đủ/Epic in PO)

5 ngày baseline pha (DESIGN/DEV/TEST/PENTEST/R4GOLIVE) được suy ra tuần tự từ Start Date (T1), cộng dồn số ngày làm việc theo tỷ trọng 20% / 30% / 30% / 10% / 10% trên tổng số ngày làm việc TTM-CNTT của Epic (15 hoặc 30 ngày tuỳ độ phức tạp, mục 6.1/6.3). Vì tỷ trọng từng pha thường ra số ngày lẻ, hệ thống làm tròn theo từng pha để tổng cộng dồn luôn khớp chính xác tổng số ngày TTM-CNTT:

  • DESIGN: làm tròn lên (ceiling).
  • DEV, TEST, PENTEST: làm tròn xuống (floor), tính tiếp nối từ ngày cộng dồn của pha trước.
  • R4GOLIVE: không dùng số ngày làm tròn theo chuỗi tích luỹ ở trên — được gán trực tiếp bằng Start Date + (tổng số ngày làm việc TTM-CNTT − 1) ngày làm việc, để đảm bảo ngày baseline R4GOLIVE luôn trùng khớp tuyệt đối với Target TTM-CNTT tổng (mục 6.1), không lệch do sai số làm tròn cộng dồn qua 4 pha trước.
Ví dụ Epic phức tạp (30 ngày TTM-CNTT): DESIGN chiếm ⌈30×20%⌉ = 6 ngày; DEV/TEST mỗi pha làm tròn xuống theo tỷ trọng 30%; PENTEST làm tròn xuống theo 10%; R4GOLIVE luôn rơi đúng ngày làm việc thứ 29 kể từ Start Date (30 − 1), bất kể tổng 4 pha trước cộng dồn ra bao nhiêu ngày.

8. Dữ liệu bất thường (không còn bị chặn import)

Một Epic được đánh dấu dữ liệu bất thường khi: thiếu hẳn Start Date, hoặc có R4G Date sớm hơn Start Date, hoặc có Due Date sớm hơn T0. Hai rule sau trước kia chặn import hoàn toàn (dòng bị loại khỏi issues) — nay chỉ còn là WARNING không chặn: R4G Date sớm hơn Start Date; Due Date sớm hơn T0.

Epic bị đánh dấu:

  • Bị đẩy xuống cuối bảng và tô nền highlight trên cả 3 màn hình giám sát.
  • Cột Nhận xét hiện “Không tính được” thay vì badge Cảnh báo/Fail hay “Đạt TTM”.
  • Riêng khi Start Date vẫn có (chỉ R4G/Due Date phi logic): dải TTM-CNTT vẫn vẽ bình thường — baseline theo Start Date, thực tế = Start Date → hôm nay (bỏ qua ngày phi logic thay vì vẽ ngược).
Lý do thiết kế: để user chủ động nhận biết và làm sạch dữ liệu nguồn trên Jira, thay vì Epic bị âm thầm loại khỏi hệ thống mà không ai biết.

9. Lịch sử cảnh báo tích luỹ

Khác với cảnh báo hiển thị trên bảng (tính real-time), bảng epic_alert_history "đóng băng" đúng trạng thái cảnh báo Fail TTM-CNTT tổng thể tại ngày import: mỗi khi Epic được tính là Cảnh báo muộn hoặc Fail TTM ở một lần import, hệ thống ghi 1 dòng gồm loại cảnh báo, trạng thái Epic lúc đó và ngày cảnh báo — không ghi đè, tích luỹ theo thời gian để tra cứu sau này.

Dữ liệu này phục vụ 2 việc trên màn hình rút gọn/đầy đủ:

  • Icon tam giác vàng cạnh Epic Key mở panel liệt kê toàn bộ lịch sử cảnh báo, sắp xếp theo ngày.
  • Quyết định Epic đã Released có tiếp tục hiển thị trên màn rút gọn hay không (màn đầy đủ/Epic in PO/Dashboard không áp dụng rule ẩn này).
Cảnh báo theo từng pha (DEV/TEST/PENTEST của màn đầy đủ, cũng ghi vào bảng này) hiện tạm tắt ghi nhận do giới hạn kết nối của hạ tầng DB miễn phí (code vẫn còn nguyên, chỉ chưa gọi). Tương tự, epic_milestone_history (mốc DESIGN_DONE/DEV_DONE/TEST_DONE) cũng tạm tắt ghi — trạng thái hoàn thành từng pha của Epic đầy đủ hiện tính live từ status Story/Subtask hiện tại mỗi lần tải trang, không phụ thuộc lịch sử này.

9.2. Dòng thời gian cảnh báo theo đợt (epic_alert_timeline)

Song song với epic_alert_history (chỉ ghi 1 dòng rời rạc mỗi lần rơi vào Cảnh báo muộn/Fail), bảng epic_alert_timeline theo dõi 5 loại cảnh báo của mỗi Epic dưới dạng các "đợt" (run) có khoảng ngày bắt đầu/kết thúc, cho phép biết chính xác Epic đã ở trạng thái cảnh báo đó liên tục từ ngày nào đến ngày nào, không chỉ ngày phát hiện:

  • FAIL_TTM_CNTT — Fail TTM-CNTT tổng thể (mục 7.3)
  • LATE_TTM_CNTT — Cảnh báo muộn TTM-CNTT theo trạng thái hiện tại (mục 6.2)
  • FAIL_TTM_E2E — Fail TTM-E2E (mục 7.3)
  • MISSING_START_DATE — Epic thiếu Start Date
  • DATA_ANOMALY — Dữ liệu bất thường (mục 8)

Mỗi lần aggregateBatchData() chạy (import thủ công, import tự động qua API, hoặc "Chạy lại" lớp dữ liệu), hệ thống tính lại cả 5 trạng thái này cho từng Epic bằng đúng những hàm dùng chung mà các màn hình giám sát dùng để hiển thị hôm nay (hasDataAnomaly, resolveTtmE2eRelease, …) — nên lịch sử ghi lại không bao giờ "lệch pha" so với những gì màn hình đang hiển thị. So sánh với các "đợt" đang mở trong DB: đợt đang mở và vẫn còn đúng → nối dài thêm; đợt đang mở nhưng hết đúng → đóng lại (gán end_date); trạng thái mới xuất hiện → mở đợt mới. Toàn bộ thao tác ghi trong 1 lần import được gộp thành tối đa 3 câu lệnh SQL theo lô, không ghi từng Epic một. Dữ liệu này phục vụ mục "Dòng thời gian cảnh báo" trong popup Epic History ở màn hình Quản trị Epic (đầy đủ).

10. Bốn màn hình giám sát Epic

10.1. Quản trị Epic (rút gọn) (/epic-alerts) — ADMIN/SUPERADMIN/SUPERVISOR

Theo dõi tổng quan các Epic theo mốc chuẩn 30 ngày (Epic phức tạp) hoặc 15 ngày (Epic đơn giản) qua 3 cột chính: Design, In Progress, Ready4Golive, cộng cột Release. Có đủ 2 cột dải TTM-CNTT và TTM-E2E.

10.2. Quản trị Epic (đầy đủ) (/epic-alerts-15) — mọi role đã đăng nhập

Theo dõi chuyên sâu theo 5 pha mốc thời gian: Design (20%), Dev (50%), Test (80%), Pentest (90%), R4Golive (100%). Ngày baseline mỗi pha được tính tự động dựa trên số ngày làm việc tích lũy từ Start Date (T1); cột Release lấy baseline từ T0 + tiêu chí TTM-E2E, độc lập với Start Date.

10.3. Epic in PO (/epic-in-po) — mọi role đã đăng nhập

Cùng dữ liệu/logic với màn (đầy đủ), chỉ lọc còn Epic đang ở trạng thái To Do, In PO hoặc Released — dùng để theo dõi Epic chưa/vừa qua giai đoạn lập kế hoạch.

10.4. Dashboard (/dashboard) — mọi role đã đăng nhập

Thống kê tổng hợp theo dự án: số Epic, phân bố trạng thái, số lượng Fail TTM-CNTT/Fail TTM-E2E/Cảnh báo sớm/muộn, tỷ lệ Đạt TTM, Epic sắp đến hạn, top Epic cần chú ý. Không có bảng tổng hợp riêng — tính live từ cùng dữ liệu 3 màn hình trên. Role SUPERVISOR/SUPERADMIN/ADMIN, hoặc USER có từ 4 dự án có dữ liệu Epic trở lên, phải chọn 1–3 dự án trước khi xem số liệu.

10.5. Quy tắc hiển thị & Lịch sử Cảnh báo (rút gọn/đầy đủ)

  • Epic ở trạng thái khác Released: luôn hiển thị.
  • Màn rút gọn: Epic ở trạng thái = Released chỉ hiển thị nếu từng có lịch sử Cảnh báo muộn/Fail TTM; nếu chưa từng bị cảnh báo, Epic sẽ biến mất khỏi danh sách sau khi Released. Màn đầy đủ/Epic in PO/Dashboard không áp dụng rule ẩn này — luôn hiện mọi Epic trong phạm vi được phân quyền.
  • Icon tam giác vàng ở cột Epic mở ra popup Epic History để tra cứu tích lũy cảnh báo Fail TTM-CNTT qua các đợt import.
  • Epic có dữ liệu bất thường (mục 8) luôn bị đẩy xuống cuối bảng và tô nền highlight trên cả 3 màn hình giám sát Epic.

13. Popup quảng cáo (AD Popup)

Cấu hình tại menu avatar người dùng → Quản lý chung → Popup quảng cáo, chỉ SUPERADMIN thấy và chỉnh sửa được. Popup hiển thị cho mọi user đã đăng nhập (không phân biệt role) khi đủ điều kiện, ngay khi họ vào một màn hình bất kỳ sau đăng nhập (không hiện ở trang login).

13.2. Chế độ "Bắt buộc xem"

Mặc định (forceView = false): popup hiện nút X ngay từ đầu và tự động đóng sau timeoutSeconds giây, người dùng có thể đóng sớm bất cứ lúc nào.

Khi bật Bắt buộc xem (forceView = true): popup không có nút X và không tự đóng trong timeoutSeconds giây đầu — thay vào đó hiện bộ đếm ngược ở vị trí nút X. Hết thời gian đếm ngược, nút X mới xuất hiện để người dùng tự đóng (không tự động đóng nữa).

13.3. Bố cục nội dung popup

Tiêu đề chiến dịch luôn hiển thị in đậm, cỡ chữ lớn hơn nội dung 1 cấp, căn trái (không cấu hình được, áp dụng cho mọi popup). Phần nội dung thông điệp không có canh lề mặc định (theo dòng chảy tự nhiên) — nếu người soạn dùng WYSIWYG đặt canh trái/giữa/phải cho một đoạn cụ thể thì hiển thị đúng theo lựa chọn đó.

13.4. Vòng đời hiển thị & theo dõi lượt xem

  • GET /api/ad-popups/active — mọi user đã đăng nhập gọi 1 lần khi tải lại toàn trang, trả về danh sách popup còn đủ điều kiện cho user đó: đang Active, trong khoảng ngày hiệu lực, và chưa đạt số lần hiện tối đa của riêng user này.
  • Chỉ hiện 1 popup tại một thời điểm (theo hàng đợi, popup đầu tiên đủ điều kiện); đóng popup này mới hiện popup tiếp theo trong hàng đợi (nếu có), không cần tải lại trang.
  • Mỗi lần popup thực sự hiển thị, hệ thống gọi POST /api/ad-popups/[id]/impression để cộng dồn lượt hiện cho user đó — tính tại thời điểm hiện, không phải thời điểm đóng.
  • Nút "Test Popup" trong form cấu hình cho phép SUPERADMIN xem trước popup đang soạn (kể cả khi chưa lưu) với đúng hành vi hiển thị thật, không tính vào số lần hiện.
Nội dung HTML (thông điệp) được xử lý qua bộ lọc làm sạch nội bộ (loại bỏ <script>, thuộc tính on*, URL javascript:, …) trước khi lưu — đây không phải một thư viện sanitize chuyên dụng, ranh giới an toàn thực tế là chỉ SUPERADMIN mới soạn được nội dung này.

14. Banner thông báo (Information Banner)

Khác với Popup quảng cáo (che màn hình, cần tương tác), đây là 1 dòng thông báo nhỏ, không chặn thao tác, gắn cố định vào layout của từng màn hình. Banner vẫn hiển thị cho mọi user đã đăng nhập (không phân biệt role) khi đủ điều kiện — chỉ việc cấu hình bị giới hạn SUPERADMIN.

14.1. Hai loại banner

  • Banner mặc định (DEFAULT) — hiển thị trên mọi màn hình đã gắn InfoBannerDisplay. Tại một thời điểm chỉ tồn tại tối đa 1 banner mặc định đang active (ràng buộc unique index ở tầng CSDL, kèm bước "hạ cấp" banner mặc định cũ trong cùng transaction khi lưu banner mặc định mới).
  • Banner theo màn hình (PER_SCREEN) — chỉ hiển thị trên đúng 1 màn hình được chọn (screenKey = pathname, lấy từ cùng danh sách màn hình dùng cho tiêu đề trang). Không giới hạn số lượng — có thể có nhiều banner theo màn hình active cùng lúc, mỗi màn hình vẫn chỉ hiện banner PER_SCREEN của riêng nó.

14.3. Vị trí hiển thị & kiểu dáng

Mỗi màn hình tự mount InfoBannerDisplay vào đúng vị trí layout của mình (không có 1 vị trí chung toàn cục trong AppShell). Trên các màn hình giám sát Epic (Quản trị Epic đầy đủ/rút gọn, Epic in PO), banner mặc định và banner riêng được đặt ngay trên bảng danh sách Epic (mặc định trước, riêng màn hình sau) — dòng trạng thái dữ liệu (thời điểm lớp dữ liệu mới nhất) đặt dưới bảng, thay vì xen giữa banner như thiết kế cũ. Mọi màn hình đều có 1 khoảng cách dòng giữa vùng bộ lọc/toolbar và banner gần nhất.

Banner mặc định và banner riêng hiển thị đồng thời nếu cả hai cùng đủ điều kiện cho màn hình đó — không có cái nào ẩn cái nào; nếu không có banner nào đủ điều kiện, khu vực này không chiếm chỗ (không render placeholder rỗng). Banner không có nền màu/viền — chỉ gồm icon "(i)" và chữ màu --text-muted; riêng banner mặc định có icon "(i)" nổi bật hơn (màu accent) để phân biệt với banner theo màn hình.

Danh sách các màn hình đã gắn banner: Nguồn dữ liệu (/), Dashboard, 3 màn hình giám sát Epic, và toàn bộ màn hình Quản trị hệ thống (Quản lý User/Domain/Dự án, Cấu hình ngày nghỉ, Cấu hình cảnh báo, Ma trận phân quyền, Sao lưu/Phục hồi dữ liệu, Tài liệu sản phẩm).

Công nghệ

15. Tech stack

Tổng quan công nghệ nền của hệ thống — quy trình nghiệp vụ Import/ETL đã mô tả chi tiết ở mục 3, mục này chỉ nêu lớp công nghệ/hạ tầng bên dưới.

Frontend

Next.js 16 (App Router, React 19) + TypeScript, Tailwind CSS 4. Toàn bộ màn hình là Client Component ('use client'), gọi thẳng các Route Handler nội bộ qua fetch, không dùng thư viện quản lý state/data-fetching riêng (React state + useMemo).

Backend

Next.js Route Handlers (src/app/api/**/route.ts) chạy trên Node.js — vừa là API vừa là nơi phục vụ giao diện (không có server Express/NestJS riêng). Truy vấn CSDL bằng SQL thuần qua driver pg (node-postgres), không dùng ORM.

Xác thực

Tự xây (không dùng NextAuth/Clerk…): mật khẩu băm bằng bcrypt, phiên đăng nhập lưu ở bảng auth_sessions (token băm, có hạn dùng 2 giờ hoặc 24 giờ nếu "Ghi nhớ đăng nhập"), gắn vào cookie HTTP-only phía trình duyệt. Phân quyền RBAC theo 4 role cố định (mục 2), kiểm tra ở từng Route Handler qua hàm dùng chung requireUser().

Cơ sở dữ liệu

PostgreSQL, chạy song song tối đa 3 profile kết nối (local / Aiven / Supabase, mục 5) chọn qua biến môi trường DB_CONNECTION. Schema quản lý bằng migration có đánh version trong db/migrations, áp dụng thủ công cho từng profile qua script scripts/migrate-db.js — không tự động chạy migration khi deploy.

15.1. Import/ETL — lớp công nghệ

Chi tiết quy trình nghiệp vụ xem mục 3; về mặt công nghệ, import xử lý theo mô hình adapter:

  • src/lib/adapters/pure-jira-export-adapter.ts — đọc CSV export gốc từ Jira (nhiều cột, nhiều loại issue).
  • src/lib/adapters/py-jira-api-adapter.ts — đọc CSV theo cấu trúc phẳng do script Python (gọi Jira REST API) xuất ra, hỗ trợ thêm các cột phân cấp Epic → Story → Subtask.
  • Cả 2 adapter chuẩn hoá dữ liệu thô về cùng 1 kiểu issue nội bộ trước khi ghi vào CSDL — pipeline validate/ghi/tổng hợp phía sau (mục 3.2) dùng chung, không phụ thuộc adapter nào.
  • Không dùng nền tảng ETL/scheduler ngoài (Airflow, n8n…) — "ETL" ở đây gói gọn trong chính Route Handler xử lý import (đồng bộ, chạy trong 1 request HTTP), kích hoạt bằng tay qua UI hoặc bằng script Python gọi API tự động (mục 3.3).
